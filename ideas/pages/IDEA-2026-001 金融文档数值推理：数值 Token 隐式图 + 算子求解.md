# 金融文档数值推理：数值 Token 隐式图 + 算子求解

## 原始想法

我来描述一下我这个过程啊。就是当时呢我们想去处理金融文档当中的这种数值问题，去做一些统计啊，然后做一些计算之类的任务呢。那么我的逻辑，那我们当时的逻辑就是首先我们先利用正则的手段先把所有的数值全部抽取出来，然后呢根据以数值为中心向它周边扩展，去获取它的周边信息。拿到信息之后呢，我们去做一个，你拿到周边信息之后呢，让， OK， 这这是这是一部分，然后让大模型去进行一个抽取。哎然后让大模型对于这个信息进行一个抽取，以数值为中心，然后我们把它的一些字段给它抽取出来。然后呢这就形成了一个数值 token。拿到数值 token 之后呢我们可以去进行一个，呃，那么数值 token 全部存下来之后，本质上来说呢它就是一个隐式的关系图。那么我的逻辑是首先去找到所有的，我们在根据 query 进来的问题的时候呢，我们去动态解析出这个问题应该怎么解决那就是动态的去发现这个计算子图。就是发现这个隐式的图嘛，是一个子图。找到这个隐式子图之后呢我们把它放到算子里边进行计算。那么算子如果是只是简单加减乘除四的运算的话，那么直接放入就好。但是如果是符合的复杂的运算我们可以进行这一个，我们需要让大模型去编写算子的呃求解解解，需要编写求解计划，然后让算子进行一个排列，最终得出答案。大概就是这个逻辑啊。

## 核心设想

把金融文档中的数值问答拆成"离线建图 + 在线解题"两段:

1. **离线:以数值为中心构建 Token**
   - 用正则把文档中的数值全部抽出来。
   - 以每个数值为锚点向周边扩展取上下文窗口。
   - 让 LLM 围绕该数值抽取结构化字段(主语义/口径/单位/时间/科目等),得到一个"数值 Token"。
   - 全部 Token 落库后,它们之间天然形成一张**隐式关系图**(同表求和项、父子科目、同比/环比、跨段引用等)。

2. **在线:Query 驱动的子图发现 + 算子求解**
   - Query 进来后,先动态解析"这个问题要怎么算",在隐式图上定位一个**计算子图**。
   - 把该子图送入算子执行层:
     - 简单四则运算 → 直接走确定性算子。
     - 复合/复杂运算 → 由 LLM 先写求解计划(算子编排),再按计划调度算子得到答案。

## 事实(来自原始口述)

- 应用场景:金融文档中的数值类任务,目标是统计与计算。
- 数值抽取采用**正则**,不是模型抽取。
- 每个数值的周边信息通过"以数值为中心向周边扩展"获取。
- 字段抽取由 LLM 完成,产出被称为"数值 token"。
- 数值 token 集合被显式描述为"隐式的关系图"。
- Query 处理是"动态发现计算子图",而不是预先编排。
- 算子分两类:简单四则直接算;复杂运算由 LLM 编写求解计划并排列算子。

## 假设(原想法隐含、未经验证)

- 正则 + 窗口能覆盖金融文档里绝大多数有效数值,且不会被表格、脚注、千分位、单位混排等噪声显著拖累。
- 以数值为中心的固定窗口足以让 LLM 准确还原该数值的口径、时间、单位、所属科目等字段。
- 数值 token 之间的关系(同/环比、求和项、父子科目、跨段引用)可以仅靠共现与字段被可靠识别,不需要显式建模表格/版式结构。
- 任意 Query 都能被稳定地映射到图上的一个连通子图,且该子图就是解题所需的最小充分集。
- LLM 编写的"求解计划 + 算子排列"在复杂运算上正确率可接受,且算子集合可枚举/可扩展。
- 用确定性算子执行最终数值计算可以规避 LLM 直接算算术时的幻觉。

## 当前判断

- 这是一条"**结构化数值抽取 + 神经-符号求解**"路线,和金融 QA 数据集(FinQA / TAT-QA 等)上的 program-of-thoughts / retriever-program-executor 范式同源,方向成立。
- 把"数值 token"当作图节点、把 Query 解析成子图再交算子执行,好处是数值计算交给确定性代码、可解释性和可复核性比直接让 LLM 答要好。
- 主要风险集中在两处:**(a) 数值及其语义字段的抽取/对齐质量**(脏数据、表格、跨页、单位口径);**(b) 从 Query 到正确子图与算子计划的映射准确率**。这两层任何一层掉链子,算子算得再准也是错的。
- "正则抽数值 + LLM 抽字段"在 2026 年看可以升级为:版面/表格结构化解析(如 PyMuPDF/pdfplumber 或专门的版面模型)+ 约束解码/函数调用式字段抽取,而不是纯窗口。
- 求解侧可以和现在的工具调用 / code-interpreter / DSL 思路对齐:把 LLM 产出的"求解计划"显式成可校验的中间表示(DSL/AST),而不是自由文本排列算子。

## 仍然有效的部分

- **数值与推理分层**:数值计算交给确定性算子、LLM 只做抽取与规划 —— 这一分工仍合理,且比端到端 LLM 算术更可靠。
- **以数值为锚点组织文档语义**:相比切片 RAG,以数值为中心的单元更贴近金融问答的颗粒度。
- **Query → 子图 → 算子**的总体三段式:检索/定位、规划、执行解耦,便于分别评测与替换实现。
- **把字段抽取交给 LLM**:相比纯规则,在科目名、口径、时间等非标准表达上仍有优势。
