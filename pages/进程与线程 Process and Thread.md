# 进程与线程 Process and Thread

## 核心内容

进程（Process）与线程（Thread）是操作系统对"正在执行的计算"的两层抽象。经典教科书（Silberschatz《Operating System Concepts》、Tanenbaum《Modern Operating Systems》）给出一个精准的分工：

- **进程是资源分配的基本单位**：每个进程拥有独立的地址空间、打开的文件描述符表、用户/组身份、信号处理表、堆、栈和代码段。OS 以进程为单位发放和回收这些资源。
- **线程是 CPU 调度的基本单位**：线程是进程内部的一条执行流，拥有独立的程序计数器、寄存器、栈和线程局部存储（TLS）；同一进程的多个线程共享地址空间和其他资源。

引入线程的根本目的是让"并发执行"和"资源隔离"解耦：进程提供隔离边界，线程在边界内提供廉价的并发。若只有进程，每个并发任务都要付出独立地址空间和进程间通信的代价；若只有线程，不同任务之间没有内存保护，一个 bug 就能拖垮整个应用。

### 进程的构成

一个进程由 OS 内核用**进程控制块（Process Control Block, PCB）**描述。Linux 的 PCB 是 `task_struct`（`<linux/sched.h>`），主要字段包括：

| 字段类别 | 典型内容 |
|---------|---------|
| 标识与凭据 | `pid`、`tgid`、`ppid`、`uid`/`gid`、命名空间 |
| 调度状态 | `state`、`prio`、`se`（CFS 调度实体）、`policy`、时间片 |
| 地址空间 | `mm`（指向 `mm_struct`，描述页表、代码/数据/堆/栈段） |
| 文件与 I/O | `files`（`files_struct`，文件描述符表）、`fs`（cwd/root） |
| 信号 | `sighand`（`sighand_struct`，信号处理函数表）、`blocked`、`pending` |
| 执行上下文 | `thread`（`thread_struct`，保存内核栈、寄存器） |
| 统计与资源 | `utime`/`stime`、`rusage`、cgroup、namespace |

进程的地址空间由若干区段组成：代码段（text，可执行、只读）、数据段（已初始化全局变量）、BSS（未初始化全局变量，零填充）、堆（动态分配，向高地址增长）、内存映射段（`mmap` 区域，含共享库与文件映射）、用户栈（向低地址增长）。内核通过页表把这些虚拟地址段映射到物理页框。

进程状态机（新建、就绪、运行、等待/阻塞、终止）已在 [[操作系统运行机制 OS Runtime Mechanisms]] 详述。

### 线程的构成

线程由**线程控制块（Thread Control Block, TCB）**描述，包含：

- **线程私有**：线程 ID（TID）、程序计数器、通用寄存器、栈（用户栈与内核栈）、线程局部存储（TLS）、信号掩码（每线程独立）、`errno`、浮点/SIMD 状态。
- **同进程共享**：地址空间（代码、堆、`mmap` 区）、文件描述符表、用户/组 ID、信号处理函数表、当前工作目录、资源限制（`getrlimit`）。

共享使线程间通信极便宜——直接读写同一内存即可，但也带来同步问题：对共享可变状态的并发访问必须用互斥锁、条件变量、信号量、读写锁或原子操作保护，否则出现数据竞争（data race）。

### 为什么需要线程

1. **响应性**：单线程程序在 I/O 阻塞时整个进程冻结；多线程可以让 UI 或事件循环在工作线程阻塞时继续响应。
2. **资源共享**：同进程线程天然共享内存与文件描述符，无需 IPC。
3. **廉价并发**：线程创建与切换比进程轻量（无需复制页表、刷新大部分 TLB）。
4. **多核并行**：在 SMP 系统上，多个线程可真正并行运行在不同 CPU 核上，是利用多核最直接的方式。
5. **模块化**：把不同性质的工作（UI、计算、I/O）分到不同线程，简化编程模型。

### Linux 的实现："没有进程，只有任务"

Linux 在架构上不严格区分进程与线程，内核调度的最小实体是 **task**，由 `task_struct` 表示。"进程"和"线程"只是创建 task 时传给 `clone(2)` 的标志位不同：

| 标志 | 作用 |
|------|------|
| `CLONE_VM` | 共享地址空间（`mm_struct`） |
| `CLONE_FS` | 共享文件系统根目录与 cwd |
| `CLONE_FILES` | 共享文件描述符表 |
| `CLONE_SIGHAND` | 共享信号处理函数表 |
| `CLONE_THREAD` | 放入同一线程组，共享 `tgid`（用户看到的 PID） |
| `CLONE_SYSVSEM` | 共享 System V 信号量撤销值 |
| `CLONE_SETTLS` | 为新线程设置 TLS |

- 调用 `fork()` 相当于 `clone(SIGCHLD, 0)`——几乎不共享任何资源，是传统意义上的"进程"。
- 调用 `pthread_create()`（glibc/NPTL）内部使用 `clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS, ...)`，是"线程"。
- 用户看到的 PID 实际上是**线程组 ID（`tgid`）**；每个线程有独立的 TID（`task_struct.pid`），但 `getpid(2)` 返回 `tgid`。`gettid(2)` 返回线程自身的 TID，`tgkill(2)` 可以向同组内指定线程发信号。

Linux 线程库经历过 LinuxThreads → **NPTL（Native POSIX Thread Library）**的演进。NPTL 自 glibc 2.4（2004 年前后）成为默认，符合 POSIX 语义、支持 1:1 模型、修复了 LinuxThreads 在信号处理、`fork` 语义和线程同步上的诸多问题。

### fork/exec 与写时复制

Unix 创建进程分两步：

1. **`fork()`**：创建一个近乎完整的子进程副本。现代内核采用**写时复制（Copy-on-Write, CoW）**——父子进程 initially 共享同一组物理页框，页表标记为只读；任一方写入时触发缺页异常，内核才复制该页。这让 `fork` 很便宜（只需复制页表与 PCB），紧随的 `execve` 几乎会立刻替换整个地址空间，CoW 避免了无用的整段复制。
2. **`execve(path, argv, envp)`**：丢弃当前地址空间，从可执行文件加载新的代码段、数据段、堆和栈，重置信号处理表，开始从 `_start` 执行。`fork` + `exec` 的组合让 shell 可以在启动子程序前做 I/O 重定向、用户切换等设置。

`vfork()` 是更极端的优化：子进程共享父进程地址空间且父进程被挂起，直到子进程 `exec` 或 `_exit`。它在 NPTL + `mmap` 时代已基本无性能优势，且语义危险，POSIX.1-2008 已将其标记为过时。

### 用户线程、内核线程与线程模型

**用户级线程（User-level thread）**：线程库在用户空间管理线程上下文，内核只看到一个执行流。优点是创建/切换极快（几十纳秒，无需陷入内核）、可自定义调度；缺点是一个线程发起阻塞式系统调用时，整个进程被阻塞（因为内核不知道进程内有多个线程），且无法利用多核。

**内核级线程（Kernel-level thread）**：每个线程由内核直接调度，可在多核上并行，阻塞一个线程不会阻塞同进程其他线程；缺点是创建/切换需要陷入内核。

由此产生三种映射模型：

| 模型 | 映射 | 代表 | 优点 | 缺点 |
|------|------|------|------|------|
| **多对一（N:1）** | 多个用户线程 → 一个内核线程 | GNU Pth、早期 Java 绿色线程、早期 GNU Portable Threads | 切换极快、可移植 | 无法并行、一个阻塞全阻塞 |
| **一对一（1:1）** | 每个用户线程对应一个内核线程 | Linux NPTL、Windows、现代 Java（HotSpot）、macOS、FreeBSD | 可并行、阻塞不互相影响、简单 | 线程数受内核限制、切换有开销 |
| **多对多（M:N）** | M 个用户线程复用到 N 个内核线程 | Solaris 传统实现、Go 的 goroutine（M:N 调度器）、Erlang BEAM、旧版 FreeBSD KSE | 兼顾并行与轻量 | 调度器复杂、上下文切换链路长、信号语义难 |

Go 的 **goroutine** 是 M:N 模型的现代代表：运行时调度器把成千上万个 goroutine 复用到少量 OS 线程（`GOMAXPROCS` 控制并行度）上，通过网络轮询器（`netpoller`）把阻塞式网络 I/O 转为非阻塞，栈初始仅 2 KB 且可动态扩缩。它本质上是**用户态协程**与 1:1 内核线程的混合。

### 进程间通信与线程同步

进程间因地址空间隔离，需要 **IPC（Inter-Process Communication）**：

- **管道（pipe）/ 命名管道（FIFO）**：字节流，半双工或双向。
- **信号（signal）**：异步事件通知，见 [[中断与异常 Interrupts and Exceptions]]。
- **消息队列（System V / POSIX `mq_*`）**：按消息边界传递。
- **共享内存（System V `shmget`/POSIX `shm_open`）+ `mmap`**：最快，需配合信号量同步。
- **信号量（semaphore）**：计数同步原语，可跨进程。
- **套接字（socket）**：含 Unix domain socket，可跨网络或本机。
- **内存映射文件**：通过 `mmap` 共享文件或匿名页。

线程间因共享内存，主要使用**同步原语**保护共享状态：

- **互斥锁（mutex）**：保证临界区互斥进入。
- **条件变量（condition variable）**：等待某个谓词成立，需与 mutex 配合。
- **读写锁（rwlock）**：多读单写，适合读多写少。
- **信号量（semaphore）**：可作互斥或计数。
- **自旋锁（spinlock）**：忙等，只适合极短临界区。
- **屏障（barrier）**：等待所有线程到达同一点。
- **原子操作（atomic）**：无锁的单变量读改写。
- **`futex(2)`**：Linux 快速用户态互斥的内核支撑，无竞争时完全在用户态完成。

错误使用同步原语会导致死锁、活锁、饥饿（分别见 [[操作系统死锁 Deadlock]]、[[活锁 Livelock]]、[[饥饿 Starvation]]）以及优先级反转。

### 上下文切换代价对比

| 切换类型 | 主要代价 | 典型量级 |
|---------|---------|---------|
| **函数调用** | 保存少量寄存器、跳转 | 纳秒 |
| **协程/用户态线程** | 保存 PC 与被调用者保存寄存器、切换栈 | 几十纳秒 |
| **线程（同进程）** | 陷入内核、保存全部寄存器、切换内核栈；地址空间不变，TLB 大部分保持有效 | 1–5 微秒 |
| **进程** | 上述 + 切换页表基址寄存器（x86 的 CR3、ARM64 的 `TTBR0_EL1`），TLB 大量失效（PCID/ASID 可缓解）、缓存冷启动 | 1–10 微秒或更高 |
| **跨核迁移** | 上述 + 缓存完全冷、可能触发 IPI/TLB shootdown | 数十微秒 |

具体代价取决于工作集大小、缓存/TLB 命中率与硬件特性（PCID、ASID、EPT）。详见 [[操作系统运行机制 OS Runtime Mechanisms]] 的上下文切换小节。

### 进程与线程的选择

| 考量 | 倾向多进程 | 倾向多线程 |
|------|-----------|-----------|
| 安全性/隔离 | 强：地址空间隔离，崩溃不互相影响 | 弱：一个线程野指针可能拖垮整个进程 |
| 共享数据 | 需 IPC，开销与复杂度高 | 直接读写共享内存，极快 |
| 创建/切换开销 | 较高 | 较低 |
| 调试与可维护性 | 简单：状态不共享 | 复杂：数据竞争、死锁、内存可见性 |
| 容错 | 单进程崩溃可独立重启 | 单线程崩溃通常终止整个进程 |
| 典型代表 | Chrome 浏览器进程模型、PostgreSQL（后端进程）、Nginx（worker 进程） | 多数 Web 服务器工作线程、Java 应用、GUI 应用 |

现代工程实践常混合使用：多进程提供故障隔离与安全边界（如 Chromium 的站点隔离、浏览器多进程架构），进程内部用多线程或异步 I/O 提升并发。

### 协程与异步运行时

协程（coroutine）/ 用户态线程是比内核线程更轻的并发抽象，完全在用户态调度，不陷入内核：

- **Go goroutine**：栈可增长、M:N 调度、`netpoller` 整合网络 I/O。
- **Python `asyncio`**：事件循环 + `async/await`，单线程协作式调度。
- **JavaScript 事件循环**：单线程、非阻塞 I/O、消息队列。
- **Rust `tokio`/`async-std`**：基于 future 的 M:N 异步运行时。
- **Erlang/Elixir BEAM**：每个 actor 是轻量进程，调度器 M:N，支持热升级与容错。
- **Java 21 虚拟线程（Project Loom）**：JVM 层的 M:N 虚拟线程，复用载体内核线程。
- **C++20 coroutine、Kotlin coroutine、C# `async/await`**：语言级协程。

协程的代价是协作式调度：一个不 `await`/`yield` 的 CPU 密集任务会阻塞整个工作线程，需要运行时或程序员主动切出。

### 常见误区

- **"线程就是轻量进程"**：不严格。线程与进程的本质差异是资源共享程度，而非创建开销；Linux 上二者都由 `clone` 创建，区别仅在共享标志。
- **"多线程一定比多进程快"**：不一定。线程的锁竞争、伪共享（false sharing）、缓存抖动可能让多线程性能反而下降；进程隔离反而避免了这些问题。
- **"多线程一定能利用多核"**：只有 1:1 或 M:N 模型可以；纯 N:1 用户线程不能并行。Python 还受 GIL 限制，同一时刻只有一个线程执行 Python 字节码。
- **"`fork` 会完整复制父进程内存"**：现代系统是写时复制，`fork` 后父子进程共享物理页，写入时才复制。
- **"线程越多吞吐越高"**：超过 CPU 核数后，额外线程主要带来上下文切换与调度开销；I/O 密集型可设较多线程，CPU 密集型通常接近核数最佳。
- **"信号按线程送达"**：在 POSIX 语义下，信号分进程导向（如 `SIGINT`、`SIGTERM`）和线程导向（如 `SIGSEGV`、`SIGFPE` 同步信号发给触发线程）；`tgkill` 可定向发送。
- **"同一进程的线程共享栈"**：每个线程有独立的用户栈和内核栈，只有堆和代码段共享。
- **"用户态线程切换不要钱"**：协程切换虽便宜（纳秒级），但仍需保存上下文、调度逻辑以及处理跨线程迁移；过度细粒度的协程也会被调度开销吞噬。
- **"`fork` 在多线程进程中是安全的"**：多线程进程调用 `fork` 时，只有调用线程被复制到子进程，其他线程持有的锁在子进程中永久锁定；在 `fork` 与 `exec` 之间只能调用异步信号安全函数，这是 POSIX 公认的坑。
