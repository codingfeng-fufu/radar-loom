# 活锁 Livelock

## 核心内容

活锁（Livelock）是并发系统中的一种**活性失败（liveness failure）**：参与的进程或线程**没有被阻塞**——它们在持续运行、不断改变自身状态——但整体上没有任何一个能推进到目标。Wikipedia 将其定义为死锁的一种特殊情形：进程状态相对于彼此不断变化，却无一取得进展。

活锁与死锁的关键区别在于**进程是否在消耗 CPU**。死锁进程挂起等待，CPU 占用为零；活锁进程"看起来很忙"，不断执行状态检查、释放与重试逻辑，却在做无用功。因此活锁往往比死锁更难诊断——监控系统看到 CPU 在跑、日志在写，但业务毫无进展。

### 经典例子

**1. 走廊让行（Polite Person Protocol）**

两个人在窄走廊相向而行，为了让路同时向同一侧闪躲，发现挡住对方后又同时向另一侧闪躲，如此反复。两人都在移动、都在"礼貌地"响应对方，但谁也通不过。这是活锁最直观的隐喻。

**2. 两个互让锁的线程**

```
线程 1:                          线程 2:
lock(A);                         lock(B);
  // 检测到对方可能需要 A          // 检测到对方可能需要 B
  unlock(A);                     unlock(B);
  wait(random_short_time);       wait(random_short_time);
  lock(A);  // 再次冲突           lock(B);  // 再次冲突
  ...                            ...
```

若两个线程使用**相同**的退避时间或确定性策略，它们会反复同步地释放、等待、再获取，永远冲突。

**3. 死锁恢复算法引发的活锁**

多个进程同时被死锁检测器判定处于死锁中，每个都执行"回滚 + 重试"。若所有进程同时回滚到同一检查点并以相同顺序重新请求资源，死锁会立即再现，检测器再次触发——系统陷入"死锁—检测—回滚—再死锁"的循环。这是 Wikipedia 明确指出的活锁典型来源。

**4. 哲学家就餐问题中的同步重试**

Dijkstra 的哲学家就餐问题中，若每位哲学家都采用"先拿左叉，若右叉被占用则放下左叉、等待一会儿再试"的策略，且等待时间相同，他们可能同步地拿起、放下，永远没人同时拿到两根叉子。

**5. 以太网冲突的极端情形**

CSMA/CD 中两个站点同时发送、冲突后若采用**确定性**（而非随机）重传定时器，会反复同时重传、反复冲突。二进制指数退避（BEB）正是为打破这种同步而设计——详见 [[随机接入协议 ALOHA CSMA CSMA-CD CSMA-CA]]。

### 与死锁、饥饿的对比

| 维度 | 死锁 Deadlock | 活锁 Livelock | 饥饿 Starvation |
|------|--------------|--------------|----------------|
| 进程是否阻塞 | 是，永久等待 | 否，持续运行 | 否，可执行但长期得不到资源 |
| 状态是否改变 | 不变 | 不断改变 | 可能改变 |
| CPU 消耗 | 无 | 有，且被浪费 | 受害者很低 |
| 是否推进 | 否 | 否 | 否（对受害者） |
| 根本原因 | 循环等待资源 | 进程间响应彼此动作导致无效循环 | 调度/分配策略不公平 |
| 典型解法 | 预防/避免/检测恢复 | 引入随机性、退避、优先级 | 公平调度、老化（aging） |

在活性属性的形式化分层中：**无死锁（no deadlock）** 严格强于 **无活锁（no livelock）**——一个保证无死锁的系统仍可能活锁；而 **无饥饿（no starvation）** 又强于无活锁，它要求每个进程最终都能获得服务。wait-free（无等待）是最强的保证。

### 常见成因

1. **对称的退避策略**：多个竞争者使用相同的确定性等待时间，导致同步重试。
2. **过度礼貌的冲突解决**：每个参与者都主动释放资源"让对方先走"，结果无人真正前进。
3. **死锁恢复算法的副作用**：多个进程同时被恢复，且恢复路径相同。
4. **消息重传风暴**：通信双方都认为对方没收到而重复发送相同消息，互相触发响应。
5. **缺乏进度保证的自旋锁**：多个线程在自旋等待同一锁，且在锁释放时以相同节奏竞争。

### 缓解与预防

**1. 随机退避与抖动（Random Backoff / Jitter）**

最常用、最有效的手段。在重试等待时间中引入随机成分，使竞争者自然错开。以太网 BEB 在第 $k$ 次冲突后从 $\{0,1,\ldots,2^{\min(k,10)}-1\}$ 中均匀随机选取退避时隙数；无线 CSMA/CA 用类似的竞争窗口 $CW$ 随机化。即使不做指数增长，加入少量随机抖动也足以打破确定性同步。

**2. 指数退避（Exponential Backoff）**

冲突次数越多，平均等待时间越长，降低重载下再次冲突的概率。但要设置上限以避免延迟无界增长。

**3. 全局唯一的进程优先级或 ID**

在冲突解决中使用稳定、唯一的进程 ID 作为打破对称的判据（如 ID 最小者优先），避免"双方都让"或"双方都抢"。代价是低优先级进程可能饥饿，需要配合老化机制。

**4. 强制资源获取顺序**

与死锁预防相同，对所有资源类型定义全局序，进程必须按序申请。这破坏了循环等待，也消除了"放下重拿"导致活锁的空间。

**5. 引入第三方仲裁者**

用一个中央协调者（锁管理器、事务调度器）串行化冲突决策，避免分布式对等协商中的对称响应。

**6. 检测与重启**

活锁难以静态检测，但可以在运行时监控"进程持续运行但任务无进展"的指标（如某事务反复回滚超过阈值），触发告警或强制某一方休眠较长时间。

### 检测的难点

- 活锁进程状态在变化，简单的"等待图"检测不出环（因为没有进程在永久等待）。
- CPU 利用率可能正常甚至偏高，传统的负载监控无法识别。
- 活锁可能只在特定时序下触发，难以复现。
- 需要**业务级进度指标**（事务完成率、请求成功率、单位时间有效产出）才能发现，而不能只看系统级资源使用。

### 常见误区

- **活锁就是死锁的一种，所以预防死锁就能预防活锁**：错。死锁预防（破坏四个必要条件）不一定阻止活锁——进程没有循环等待，但仍可在"释放—重试"循环中空转。
- **活锁进程是阻塞的**：错。活锁的定义特征就是进程未被阻塞、在主动执行。
- **加随机延迟一定能解决活锁**：随机退避能显著降低活锁概率，但在理论上不保证完全消除；要严格保证需用无等待（wait-free）或无锁（lock-free）算法并证明进度属性。
- **CPU 忙就说明系统在干活**：活锁恰恰是"忙而无功"，监控必须包含业务进度指标。
- **活锁只出现在操作系统内核**：活锁在分布式系统、数据库事务、网络协议、并发应用中同样常见，是通用的并发问题。
