# 流量控制常见方式 Flow Control

## 核心内容

流量控制（Flow Control）是点对点通信中协调发送方与接收方速率差异的一组机制，核心要解决的问题是：**发送方推送数据的速度不能超过接收方处理/缓存的速度**，否则接收方缓冲区溢出、数据丢失。它与拥塞控制（Congestion Control）目标不同——流量控制管的是"接收方跟不上"，拥塞控制管的是"网络本身承载不了"；但两者在 TCP 中以"发送窗口 = min(rwnd, cwnd)"的方式协同工作。

经典流量控制方式按发展脉络包括：停等协议、滑动窗口协议（回退 N 帧、选择重传）、TCP 基于接收窗口的流控、基于速率的流控与背压。

### 一、停等协议 Stop-and-Wait / Stop-and-Wait ARQ

**原理**：发送方每发送一个帧就停下来，等待接收方的确认（ACK）；收到 ACK 后才能发送下一帧；若超时未收到 ACK 则重传。若帧或 ACK 出错/丢失，重传同一帧。

**信道利用率推导**：设帧传输时延为 $T_t$（即"把整个帧送上线路所需时间"，= 帧长 $L$ / 数据率 $R$），信号传播时延为 $T_p$（= 距离 $d$ / 信号速度 $c$），忽略 ACK 帧长和处理时延，则一个 RTT 周期为 $T_t + 2 T_p$，其中真正用于发送数据的时间只有 $T_t$，因此停等协议的信道利用率：

$$
U_{\text{SW}} = \frac{T_t}{T_t + 2T_p} = \frac{1}{1 + 2a}, \quad a = \frac{T_p}{T_t}
$$

其中 $a$ 是"带宽×时延积" BDP 归一化后一个帧所需时间占比的度量。$a$ 越大（高速长距离链路），利用率越低。例如 $T_p = 20\text{ ms}$，$T_t = 1\text{ μs}$（1KB 帧在 1 Gbps 链路上），则 $U \approx 1/40000 \approx 0.0025\%$，几乎完全浪费带宽——这就是为什么停等只适合低速短距离场景。

**典型问题与对策**：
- **重复帧**：ACK 丢失时发送方重传，接收方会收到重复帧——通过给帧编号（0、1 交替 1 bit 序号）解决。
- **死锁**：帧或 ACK 完全丢失时双方都在等——通过超时定时器解决。
- **应用**：早期串行通信、TFTP（简单文件传输）、一些低速传感器网络。

### 二、滑动窗口协议 Sliding Window

**核心思想**：允许发送方在等待 ACK 之前连续发送多个帧（窗口大小 $W$），让"在途数据"填满发送端到接收端之间的"带宽管道"，从而把信道利用率从 $1/(1+2a)$ 提升到接近 1。发送方维护"发送窗口"：一组已发送但尚未被确认的帧序号；接收方维护"接收窗口"：一组允许接收的帧序号。每收到一个 ACK，窗口向前滑动一格。

**信道利用率**：当 $W \geq 1 + 2a$ 时管道被填满，$U \approx 1$。对带宽-时延积 $\text{BDP} = R \times \text{RTT}$，理想窗口大小应为：

$$
W_{\text{理想}} = \left\lceil \frac{\text{BDP}}{L} \right\rceil = \left\lceil \frac{R \cdot \text{RTT}}{L} \right\rceil
$$

单位是"帧"，也可直接用字节表示（TCP 就是这么做的）。

按接收窗口大小与确认策略不同，滑动窗口分两大类：

#### 1. 回退 N 帧 Go-Back-N（GBN）
- **发送窗口**：$1 < W_s \leq 2^k - 1$（$k$ bit 序号，例如 $k=3$ 则 $W_s \leq 7$）。
- **接收窗口**：$W_r = 1$（只按序接收）。
- **确认方式**：累积确认（cumulative ACK）——ACK $n$ 表示"$n-1$ 及以前都收到了，期望序号为 $n$"。
- **出错时行为**：发送方超时后重传从最早未确认帧起的**所有**已发帧；接收方丢弃所有失序帧（不缓存）。
- **优缺点**：接收方实现简单（无需缓存失序帧）；但高误码率或大窗口下大量不必要重传，带宽浪费严重。

#### 2. 选择重传 Selective Repeat / Selective Reject（SR）
- **发送窗口**：$W_s \leq 2^{k-1}$（$k$ bit 序号）。
- **接收窗口**：$W_r = W_s$（缓存失序帧）。
- **确认方式**：独立确认（selective ACK）——对每个正确收到的帧单独发 ACK，即使它失序也先缓存。
- **出错时行为**：发送方只重传超时或 NAK 的那一帧，不牵连后续正确帧。
- **优缺点**：高误码率（卫星、无线）下效率显著优于 GBN；但接收方需要缓存、实现复杂，且序号空间要减半以避免新旧序号重叠。

**GBN vs SR 对比**：

| 维度 | GBN | SR |
|---|---|---|
| 发送窗口上限 | $2^k - 1$ | $2^{k-1}$ |
| 接收窗口大小 | 1 | $W_s$ |
| 缓存失序帧 | 否 | 是 |
| 确认方式 | 累积 ACK | 独立/选择 ACK（SACK） |
| 重传粒度 | 回退重传所有未确认帧 | 只重传出错帧 |
| 复杂度 | 低 | 高 |
| 适用场景 | 低误码率、短距离 | 高误码率（无线/卫星） |

### 三、TCP 基于接收窗口的流量控制

TCP 把滑动窗口思想应用在字节级（而非帧级），实现端到端流量控制（RFC 793 §3.7）。

- **接收窗口 rwnd（Receiver Window）**：接收方在 TCP 首部的 Window 字段（16 bit，加 WSopt 窗口缩放选项后最大约 1 GB）通告自己还能接收多少字节的空闲缓冲区大小。每次 ACK 都携带最新 rwnd。
- **发送方限制**：发送方在途未确认数据量（in-flight）必须满足：
$$
\text{in-flight} \leq \min(\text{cwnd}, \text{rwnd})
$$
其中 cwnd 是拥塞窗口（拥塞控制输出），rwnd 是流控窗口（接收方通告）。
- **零窗口与 Zero Window Probe**：接收方缓冲区满时会通告 rwnd=0，发送方停止发送。为防止"接收方后续发的非零窗口更新丢失"导致死锁，发送方会定期（persist timer）发送 1 字节的窗口探测（Window Probe），强迫接收方重新通告窗口。
- **Silly Window Syndrome（糊涂窗口综合症）**：当接收方每次只腾挪出少量字节就通告 rwnd、发送方又马上发小报文时，会产生大量 40 字节头 + 1 字节有效载荷的低效小包。解决：
  - 接收端 Clark 算法：不马上通告小窗口，攒到 MSS 或缓冲区一半再通告。
  - 发送端 Nagle 算法（RFC 896）：未确认数据在途时，积攒小数据直到攒够 MSS 或收到所有 ACK 再发。
- **Delayed ACK**：接收方不立即对每个报文都 ACK，而是等待一段时间（通常 ≤200ms）或等反向有数据捎带，减少纯 ACK 报文；但对立即 ACK 的场景（快速重传需要）保留快速路径。

### 四、其他流量控制方式

#### 1. 基于速率的流控 Rate-Based Flow Control
发送方不看接收方窗口，而是根据显式的速率限制发送，常见于实时音视频、ATM ABR（Available Bit Rate，通过 RM 资源管理信令反馈允许速率）、HTTP/2 和 HTTP/3 的服务端/客户端流控（基于 credit 令牌）。QUIC 也在应用层实现了类似 TCP 的流控（每个 stream + 整个 connection 两级 credit-based 窗口）。

#### 2. XON/XOFF（软流控）
串行通信/终端场景下，接收方快跟不上时给发送方发 XOFF（Ctrl+S, ASCII 19）字符要求暂停，缓过来后发 XON（Ctrl+Q, ASCII 17）恢复。带外信号，不依赖序号/超时。

#### 3. 硬件流控 RTS/CTS、DTR/DSR
RS-232 串行口通过额外物理信号线（Request to Send / Clear to Send）做带外硬件握手，避免 XON/XOFF 被数据本身误识别的问题。

#### 4. 背压（Backpressure）
分层网络中，当下游节点/层处理不过来时，沿反向逐跳向上游传播"减速"信号（例如路由器向输入端口、再向相邻路由器发拥塞信号）。数据中心网络中的 PFC（Priority-based Flow Control, IEEE 802.1Qbb）就是链路级背压的现代形式，用来实现无损以太网（RoCE 等场景必需）。

#### 5. 信用/令牌式流控 Credit-Based
- PCIe、InfiniBand、HTTP/2/3 等：接收方预先向发送方发放"信用"，发送方每发一个数据单元消耗一份信用，接收方处理完再归还信用。比窗口式更灵活（支持多优先级、多流独立计量）。

### 五、关键假设、局限与常见误区

- **误区 1：流量控制 = 拥塞控制**。两者机制不同、目标不同：流控保护接收方，拥塞控制保护网络；TCP 中两者分别通过 rwnd 与 cwnd 限制发送速率，取 min。
- **误区 2：窗口越大越快**。窗口超过 BDP 不会提升吞吐，反而会让队列积压、增加 RTT、触发丢包；实际最优窗口约为 BDP。
- **误区 3：GBN 和 SR 是不同协议**。它们是同一滑动窗口思想下接收窗口大小的两种极端：$W_r = 1$ 即 GBN，$W_r = W_s$ 即 SR，中间还有其他变体。
- **误区 4：TCP 的窗口大小总是 64 KB**。这是 16 bit Window 字段的原始上限，RFC 7323 的 Window Scale 选项把左移位数扩到 14 bit，使最大窗口到约 1 GB，适应长肥管道（long fat network, LFN）。
- **Nagle 与 Delayed ACK 的交互**：两者同时开启时可能出现"写 → 等 ACK 不发 → ACK 等 200ms"的 200ms 延迟，必要时通过 TCP_NODELAY 关闭 Nagle（如实时交互场景）。
- **根本假设**：所有流控机制都依赖"接收方能够反馈自己的接收能力/速率"这一带外或带内反馈通道；反馈延迟越大、越不可靠，所需缓冲与窗口越大。
