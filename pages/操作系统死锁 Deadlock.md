# 操作系统死锁 Deadlock

## 核心内容

死锁是指一组进程中的每个进程都持有至少一个资源，同时等待被同组中另一个进程持有的资源，导致所有进程永久阻塞、无法继续执行的状态。死锁不是普通的"慢"或"饥饿"——进程在逻辑上已经不可能自行推进，只能依赖外部干预。

死锁的根源在于**资源的竞争性获取**与**进程推进顺序的不可预测性**。当多个进程以不同顺序申请多个不可抢占资源时，就可能形成循环等待链。

### 四个必要条件（Coffman Conditions）

死锁发生当且仅当以下四个条件**同时成立**，缺一不可：

1. **互斥（Mutual Exclusion）**：资源一次只能被一个进程使用。
2. **持有并等待（Hold and Wait）**：进程持有至少一个资源，同时等待获取被其他进程持有的额外资源。
3. **不可抢占（No Preemption）**：资源只能由持有者自愿释放，不能被强行剥夺。
4. **循环等待（Circular Wait）**：存在一个进程等待环 $\{P_0, P_1, \ldots, P_n\}$，其中 $P_i$ 等待 $P_{i+1}$ 持有的资源，而 $P_n$ 等待 $P_0$ 持有的资源。

其中循环等待隐含了持有并等待，但单独列出有助于设计预防策略。

### 资源分配图（Resource-Allocation Graph）

用有向图精确定义死锁。顶点分为进程节点 $P = \{P_1, \ldots, P_n\}$（圆圈）和资源类型节点 $R = \{R_1, \ldots, R_m\}$（矩形，内部圆点表示实例数）。边有两种：

- **请求边** $P_i \rightarrow R_j$：进程 $P_i$ 请求资源 $R_j$ 的一个实例
- **分配边** $R_j \rightarrow P_i$：资源 $R_j$ 的一个实例已分配给进程 $P_i$

关键判据：
- 图中**无环** → 系统无死锁
- 图中**有环**，且每种资源只有一个实例 → 必然死锁（环即死锁）
- 图中**有环**，但资源有多个实例 → 可能死锁，也可能不死锁（取决于后续请求与释放顺序）

### 处理死锁的四类策略

| 策略 | 核心思想 | 代价 |
|------|---------|------|
| **预防 Prevention** | 破坏四个必要条件中的至少一个 | 资源利用率低、可能降低并发性 |
| **避免 Avoidance** | 动态检查资源分配状态，始终保持系统处于安全状态 | 需预知进程最大资源需求、运行时开销 |
| **检测与恢复 Detection & Recovery** | 允许死锁发生，定期检测并恢复 | 检测开销、恢复时丢失计算成果 |
| **忽略 Ostrich Algorithm** | 假装死锁不会发生，由用户重启 | 实现最简单；死锁真发生时系统挂起 |

#### 死锁预防

逐一破坏必要条件：

- **破坏互斥**：对于可共享资源不做互斥（但某些资源本质上不可共享，如打印机）。
- **破坏持有并等待**：要求进程在开始执行前一次性申请所有需要的资源。问题是资源利用率低（长时间占用不用的资源），且可能导致饥饿。
- **破坏不可抢占**：若进程持有资源后又申请被拒，则必须释放所有已持有资源，之后重新申请。适用于 CPU 寄存器、内存等可保存恢复状态的资源，不适用于打印机等不可抢占资源。
- **破坏循环等待**：对所有资源类型进行全局编号排序，要求每个进程按编号递增顺序申请资源。这是最常用的预防手段，但可能导致进程提前申请不需要的资源。

#### 死锁避免

避免策略要求每个进程预先声明对每种资源的**最大需求**，系统在每次分配前检查该分配是否使系统进入不安全状态。

**安全状态**：存在一个进程执行序列 $\langle P_1, P_2, \ldots, P_n \rangle$，使得对于每个 $P_i$，其剩余资源请求可由当前可用资源加上所有 $P_j$（$j < i$）持有的资源满足。安全状态下不会发生死锁；不安全状态不一定死锁，但有死锁风险。

**单实例资源——资源分配图算法**：引入"声明边"（claim edge）$P_i \dashrightarrow R_j$，表示进程将来可能请求该资源。当进程实际请求时，声明边变为请求边；分配前先检查把请求边转为分配边后图中是否会出现环。无环才分配。

**多实例资源——银行家算法（Banker's Algorithm）**：由 Dijkstra 提出，类比银行确保现金不会全部分配完而无法满足所有客户。设 $n$ 为进程数，$m$ 为资源类型数，维护以下数据结构：

- `Available[m]`：每种资源的可用实例数
- `Max[n][m]`：每个进程对每种资源的最大需求
- `Allocation[n][m]`：每个进程当前已分配的资源数
- `Need[n][m]`：每个进程的剩余需求

$$\text{Need}[i][j] = \text{Max}[i][j] - \text{Allocation}[i][j]$$

**安全性检测算法**：
1. 初始化 `Work = Available`，`Finish[i] = false`
2. 找到满足 `Finish[i] == false` 且 `Need[i] ≤ Work` 的进程 $P_i$
3. 若找到：`Work = Work + Allocation[i]`，`Finish[i] = true`，回到步骤 2
4. 若所有 `Finish[i] == true`，则状态安全；否则不安全

时间复杂度 $O(m \times n^2)$。

**资源请求算法**：进程 $P_i$ 发出请求 `Request[i]` 时：
1. 若 `Request[i] > Need[i]`，报错（超过最大声明）
2. 若 `Request[i] > Available`，进程等待
3. 试探性分配：`Available -= Request[i]`，`Allocation[i] += Request[i]`，`Need[i] -= Request[i]`
4. 执行安全性检测：安全则正式分配；不安全则回滚，进程等待

银行家算法的局限：需要预先知道最大需求（实际中往往不可知）、进程数固定、进程不能中途退出，因此实际操作系统很少采用。

#### 死锁检测与恢复

不做预防和避免时，系统需要检测死锁并恢复。

- **单实例资源**：用**等待图（Wait-for Graph）**——从资源分配图中移除资源节点，将进程间的等待关系直接连边。图中有环即存在死锁。
- **多实例资源**：使用类似银行家算法的检测算法，但不检查安全性，而是检查当前是否存在进程无法完成。

**检测时机**：每次资源请求不能立即满足时检测（精确但开销大）、定时检测、CPU 利用率低于阈值时检测。

**恢复手段**：
- **终止进程**：终止所有死锁进程（代价大但彻底），或逐个终止直到环断裂（每次终止后需重新检测）。选择终止对象时考虑进程优先级、已运行时间、已持有资源等因素。
- **资源抢占**：从部分进程强行回收资源给其他进程，直到死锁解除。需要处理选择牺牲品、回滚（rollback）到安全状态、以及防止同一进程总被选为牺牲品导致饥饿等问题。

#### 忽略策略（Ostrich Algorithm）

包括 Linux、Windows 在内的大多数通用操作系统选择忽略死锁。理由是：死锁预防/避免的运行时开销可能远大于偶发死锁带来的损失；许多死锁场景在实际中极少出现；且死锁的根本原因往往在应用程序层面（如锁的加锁顺序不一致），应由开发者负责。当死锁真的发生时，用户可以杀掉相关进程或重启系统。

### 活锁与饥饿的区别

- **活锁（Livelock）**：进程状态在不断改变，但无法推进执行。例如两个进程都试图"礼貌地"释放资源让对方先获取，结果双方都永远无法继续。活锁中的进程没有阻塞，但在做无用功。
- **饥饿（Starvation）**：进程虽可执行，但因调度策略长期得不到所需资源，等待时间无上限。与死锁不同，饥饿进程在理论上仍可推进。

### 常见误区

- 死锁不等于系统变慢或资源不足；死锁进程在逻辑上已不可能自行推进。
- 有环不一定有死锁（多实例资源时），但死锁一定有环。
- 不安全状态不等于死锁状态——不安全只是意味着存在死锁的可能。
- 银行家算法是教学经典，但几乎没有商用操作系统实际使用。
