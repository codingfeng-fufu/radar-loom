# 操作系统运行机制 OS Runtime Mechanisms

## 核心内容

操作系统运行机制（OS Runtime Mechanisms）回答一个根本问题：**当 CPU 正在执行用户程序时，操作系统如何夺回控制权、完成自身工作、再把 CPU 交还给另一个进程？** 这不是靠 OS "周期性地检查"做到的——OS 是一段被动的事件驱动代码，它必须依靠硬件提供的中断、异常、特权级切换等机制才能介入执行。理解运行机制是理解进程调度、系统调用、I/O 与并发的基础。

OS 与普通程序的关键区别：普通程序一旦获得 CPU 就一直运行，直到它主动放弃；而 OS 必须保证即使程序死循环、不调用任何系统调用，也能被强制夺回 CPU。这要求**硬件级的异步入口**——主要就是中断。

### 进入内核的三条路径

CPU 从用户态陷入内核态只有三种方式，统称为**异常控制流（Exceptional Control Flow, ECF）**：

| 类型 | 触发源 | 同步/异步 | 典型例子 | 返回行为 |
|------|--------|----------|---------|---------|
| **中断（Interrupt）** | 外部硬件 | 异步 | 网卡收包、磁盘完成、定时器到期 | 返回到被中断的下一条指令 |
| **异常（Exception / Fault / Trap）** | 当前指令 | 同步 | 缺页、除零、非法指令、调试断点 | 故障可重新执行指令；陷阱继续下一条；中止终止进程 |
| **系统调用（System Call）** | 当前指令（主动） | 同步 | `read`、`write`、`fork`、`mmap` | 返回到 syscall 之后的下一条指令 |

严格区分术语：
- **中断**总是异步的，由 CPU 外部设备产生，与当前执行的指令无关。
- **异常**是同步的，由当前指令的执行产生，分为故障（fault，可修复后重执行，如缺页）、陷阱（trap，有意触发，如调试断点）和中止（abort，不可恢复，如硬件错误）。
- **系统调用**在分类上是一种故意的陷阱（trap），用户程序通过专用指令主动请求 OS 服务。

### 中断处理生命周期

一次硬件中断的完整路径：

1. **设备发起 IRQ**：设备通过中断线向中断控制器（PIC 或现代的 APIC/GIC）发送信号。
2. **中断控制器仲裁**：若多个中断同时到来，按优先级仲裁；对未被屏蔽的中断，向 CPU 的 INTR 引脚发信号。
3. **CPU 响应**：当前指令执行完后，CPU 保存最小状态（程序计数器、标志寄存器、当前栈指针），根据中断号查找 **中断描述符表（IDT）** 得到中断处理程序入口。
4. **特权级切换**：CPU 从用户态切到内核态，从 TSS（Task State Segment）加载内核栈，跳转到 IDT 中登记的 ISR（Interrupt Service Routine）。
5. **ISR 执行（顶半部/top-half/hardirq）**：内核保存所有被破坏的寄存器，尽快响应硬件（读走数据、确认中断），然后把耗时工作推迟。ISR 期间该中断线通常被屏蔽，不能睡眠。
6. **底半部（bottom-half）**：延迟处理不紧急的工作，机制包括 softirq、tasklet、workqueue（Linux）或 DPC（Windows）。底半部可在更安全的时刻执行，workqueue 甚至运行在进程上下文、可睡眠。
7. **中断返回（`iret`/`eret`）**：恢复寄存器，切换回原特权级和原栈，回到被中断的指令之后继续执行。

IDT 是一个最多 256 项的数组，每项是一个门描述符（中断门/陷阱门/任务门），记录处理程序入口地址和所需特权级。前 32 项保留给 CPU 异常（如 0 号除零、14 号缺页）；32–255 用于外部 IRQ 和系统调用（如 x86-32 的 `int 0x80`）。中断控制器、x86 异常向量表、顶半部/底半部、MSI/MSI-X、IPI、ARM GIC、信号等深入内容见 [[中断与异常 Interrupts and Exceptions]]。

### 系统调用流程

现代 x86-64 Linux 的系统调用流程（使用 `syscall`/`sysret` 指令，而非旧的 `int 0x80`）：

1. **用户态准备参数**：按 System V 调用约定，把系统调用号放入 `rax`，参数依次放入 `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`。
2. **执行 `syscall` 指令**：CPU 把返回地址存入 `rcx`，把 RFLAGS 存入 `r11`，从 `IA32_LSTAR` MSR 加载内核入口地址，切换到 CPL0（内核态），从 TSS 加载内核栈，跳转到入口（如 `entry_SYSCALL_64`）。
3. **内核入口**：保存所有通用寄存器到内核栈，检查系统调用号合法性，从 `sys_call_table` 查得对应处理函数。
4. **执行处理函数**：内核代表用户进程执行请求的操作（读文件、发网络包、创建进程等）。可能阻塞（此时触发调度，切换到其他进程）。
5. **返回**：把返回值放入 `rax`，恢复寄存器，执行 `sysretq` 切回用户态，从 `rcx` 恢复 RIP、从 `r11` 恢复 RFLAGS。

ARM64 使用类似机制：用户态执行 `svc #0`（Supervisor Call），CPU 跳转到异常向量表（`VBAR_EL1`）中同步异常入口，参数放在 `x0`–`x5`，系统调用号放在 `x8`。

**系统调用的开销**：一次 syscall 包含特权级切换、寄存器保存/恢复、地址空间切换（某些场景）、必要的安全检查，典型开销在几百纳秒到 1–2 微秒，比普通函数调用高 100–1000 倍。因此高性能 I/O 常使用 `epoll`/`io_uring`、批处理、`sendfile`、`mmap` 等减少 syscall 次数。

### 上下文切换（Context Switch）

当调度器决定把 CPU 从进程 A 切换到进程 B 时，发生上下文切换：

1. **保存 A 的状态**：把 A 的所有通用寄存器、程序计数器、栈指针、浮点/SIMD 寄存器写入 A 的 **进程控制块（PCB / `task_struct`）**。
2. **切换内核栈**：CPU 当前使用的内核栈切换到 B 的内核栈。
3. **切换地址空间**：把页表基址寄存器切换到 B 的页表（x86 的 CR3、ARM64 的 TTBR0_EL1），这会使部分 TLB 失效。
4. **恢复 B 的状态**：从 B 的 PCB 恢复寄存器，包括 PC 和 SP。
5. **返回用户态**：执行 `iret`/`eret`/`sysret`，CPU 开始执行 B 的用户代码。

上下文切换的主要代价不在于寄存器保存（纳秒级），而在于**缓存破坏**：新进程的工作集不在 L1/L2/TLB 中，切换后会有大量 cache miss，冷启动阶段性能骤降。一次切换的总代价通常在 1–10 微秒，工作集大时更高。

线程切换比进程切换便宜，因为同一进程的线程共享地址空间，切换时不需要更换 CR3、TLB 大部分保持有效。这是协程/用户态线程（goroutine、asyncio）进一步追求的方向——完全在用户态切换，不陷入内核，代价可低至几十纳秒。

### 进程状态机

经典的五状态进程模型：

```
  创建        调度          I/O请求或      I/O完成或
   │           │           等待事件         事件到达
   ▼           ▼              │               │
[新建] ───► [就绪] ◄─────────[运行] ────────► [等待/阻塞]
             ▲   │                           
   时间片到期│   │进程退出或终止             
             │   ▼                           
             └─ [终止]                        
```

- **新建（New）**：PCB 已创建，尚未进入就绪队列。
- **就绪（Ready）**：万事俱备，只等 CPU。
- **运行（Running）**：指令正在 CPU 上执行。单核同一时刻只有一个进程处于此态。
- **等待/阻塞（Waiting/Blocked）**：等待某事件（I/O 完成、锁、信号量），即使给它 CPU 也无法运行。
- **终止（Terminated）**：执行结束，等待回收。

关键转换：
- 就绪→运行：由调度器选择。
- 运行→就绪：被高优先级进程抢占或时间片用完。
- 运行→等待：发起阻塞式 I/O 或获取不可用的锁。
- 等待→就绪：等待的事件发生（由中断或另一个进程触发）。

注意 **阻塞与就绪的区别**：阻塞进程"在等某事发生"，就绪进程"随时可以跑但没轮到"。把阻塞进程放进就绪队列毫无意义，因为它会立刻因资源不可用再次进入等待。

### 时钟与抢占

OS 能从陷入死循环的用户程序手中夺回 CPU，完全依赖**定时器中断**：

- 硬件定时器（PIT、HPET、APIC timer、ARM Generic Timer）按固定频率（如 Linux 默认 250 Hz 或 1000 Hz，即 4 ms 或 1 ms）产生中断。
- 每次定时器中断，内核更新当前进程的时间计数；若时间片（quantum）用完，触发调度器选择另一个进程。
- 这就是**抢占式多任务（preemptive multitasking）**：进程不需要主动放弃 CPU，OS 可在任何中断点强行切换。
- 对比**协作式多任务（cooperative multitasking）**：进程必须主动 yield（如早期 Mac OS、Windows 3.x），一个不合作的进程就能挂死整个系统。

实时系统需要更精确的定时器和优先级继承等机制（见 [[饥饿 Starvation]] 中关于优先级反转的讨论）。

### 特权级模型

**x86（Ring 模型）**：CPU 提供 4 个特权级 Ring 0–Ring 3，但现代通用 OS 只使用两个：

- **Ring 0（内核态）**：可执行所有指令、访问所有 I/O、直接操作页表与硬件。
- **Ring 3（用户态）**：只能执行非特权指令，访问本进程地址空间；任何特权操作必须通过系统调用请求内核。

Ring 1、Ring 2 历史上曾设想用于驱动或服务，但主流 OS 均未实际使用。

**ARM64（异常级别 Exception Level）**：

- **EL0**：用户态（应用）
- **EL1**：内核态（OS 内核）
- **EL2**：虚拟化（Hypervisor）
- **EL3**：安全监控器（Secure Monitor / Trusted Firmware）

这种分层更干净地支持虚拟化与可信执行环境。

### 内核如何"常驻"

OS 内核并非一个持续运行的进程，而是**一组可被各种事件激活的处理程序**：

- 系统调用时，内核在"当前进程的上下文"中运行（代表该进程执行，使用该进程的内核栈）。
- 中断发生时，内核在"中断上下文"中运行（不属于任何进程，不能睡眠，使用独立的中断栈）。
- 内核线程（如 Linux 的 ksoftirqd、kswapd）则是独立运行在内核态的进程，用于执行需要进程上下文的后台工作。

这种事件驱动结构是 OS 与普通应用最本质的区别。

### 常见误区

- **"OS 在后台持续运行，定时检查系统状态"**：错。OS 没有独立的 CPU，它是被事件（中断、系统调用、异常）激活的；没有事件时 CPU 运行用户进程或进入 idle。
- **"系统调用就是函数调用"**：系统调用涉及特权级切换、寄存器保存、安全检查，开销比普通函数调用高两个数量级以上。
- **"上下文切换的主要开销是保存寄存器"**：寄存器保存只需纳秒级，真正代价是缓存/TLB 失效带来的内存访问停顿。
- **"中断处理程序可以睡眠"**：顶半部（hardirq）运行在中断上下文，不能阻塞；只有 workqueue 等进程上下文底半部可以睡眠。
- **"进程阻塞时仍然占用 CPU 等待"**：阻塞进程不占 CPU，调度器会切换到其他进程；它只会在等待事件发生时被唤醒进入就绪队列。
- **"用户进程可以直接关中断"**：关中断（`cli`）是特权指令，只能在内核态执行；若用户程序能关中断，它就能永远霸占 CPU。
- **"Ring 1/Ring 2 在现代系统中很重要"**：主流 OS（Linux、Windows、macOS）基本只用 Ring 0 和 Ring 3，中间两级是历史遗留。
