# 银行家算法 Banker's Algorithm

## 核心内容

银行家算法（Banker's Algorithm）由 Edsger W. Dijkstra 于 1965 年在《Cooperating Sequential Processes》中提出，是操作系统中最经典的**死锁避免（deadlock avoidance）**算法。它不破坏死锁的任何必要条件，而是在每次资源分配前动态检查：这次分配之后系统是否仍处于"安全状态"。只有安全时才真正分配，否则让进程等待。

算法得名于银行放贷隐喻：银行有有限现金，客户各自有授信额度；银行必须保证即使所有客户同时要求达到授信上限，也能通过安排客户依次完成还款来满足所有人，而不会出现现金枯竭、所有客户都无法完成的局面。

Dijkstra 原始版本只处理**单一资源类型**；Habermann（1969）将其扩展到**多种资源类型**，即今天教科书里的通用形式。

### 安全状态与不安全状态

- **安全状态**：存在一个进程执行序列 $\langle P_{i_1}, P_{i_2}, \ldots, P_{i_n}\rangle$，使得对每个 $P_{i_k}$，其剩余资源请求可由当前可用资源加上所有 $P_{i_j}$（$j<k$）执行完毕后释放的资源满足。这个序列称为**安全序列**。
- **不安全状态**：不存在这样的序列。不安全不等于已经死锁，但意味着系统可能进入死锁——所有进程都还没到最大需求，可一旦它们按最坏顺序继续申请，就没有安全保证了。

核心不变量：**安全状态一定无死锁；算法永远不把系统带入不安全状态。**

### 数据结构

设 $n$ 为进程数，$m$ 为资源类型数，维护以下四个结构：

| 结构 | 维度 | 含义 |
|------|------|------|
| `Available` | 长度 $m$ 的向量 | `Available[j]` 为资源 $R_j$ 当前可用实例数 |
| `Max` | $n\times m$ 矩阵 | `Max[i][j]` 为进程 $P_i$ 对资源 $R_j$ 的最大需求 |
| `Allocation` | $n\times m$ 矩阵 | `Allocation[i][j]` 为 $P_i$ 当前已持有 $R_j$ 的实例数 |
| `Need` | $n\times m$ 矩阵 | $P_i$ 还需要的资源数 |

`Need` 由其他三式导出：

$$\text{Need}[i][j] = \text{Max}[i][j] - \text{Allocation}[i][j]$$

系统总资源向量满足：

$$\text{Total}[j] = \text{Available}[j] + \sum_{i=0}^{n-1}\text{Allocation}[i][j]$$

### 安全性检测算法

伪代码：

```
Work = Available
Finish[i] = false for all i

while exists i such that Finish[i] == false and Need[i] <= Work:
    Work = Work + Allocation[i]
    Finish[i] = true

if Finish[i] == true for all i:
    return "safe"
else:
    return "unsafe"
```

直觉：找到一个"当前就能跑完"的进程，让它跑完并释放所有资源，再用扩大后的可用资源找下一个能跑完的进程。如果所有进程都能这样排进序列，则安全。

**时间复杂度**：每次找进程最坏扫描 $n$ 个、每个比较 $m$ 个分量，共 $n$ 轮，因此为 $O(m \times n^2)$。

### 资源请求算法

进程 $P_i$ 发出请求向量 `Request[i]` 时：

1. 若 `Request[i] > Need[i]`：出错，因为进程请求量超过了它先前声明的最大需求。
2. 若 `Request[i] > Available`：进程等待，因为资源当前不足。
3. **试探性分配**：
   $$\begin{aligned}\text{Available} &\leftarrow \text{Available} - \text{Request}[i]\\\text{Allocation}[i] &\leftarrow \text{Allocation}[i] + \text{Request}[i]\\\text{Need}[i] &\leftarrow \text{Need}[i] - \text{Request}[i]\end{aligned}$$
4. 对试探后的新状态调用安全性算法：
   - 若安全：试探正式生效，$P_i$ 拿到资源。
   - 若不安全：回滚上述三个更新，$P_i$ 等待。

### 完整算例

5 个进程、3 类资源（A/B/C），`Available = (3,3,2)`：

| 进程 | Max (A,B,C) | Allocation (A,B,C) | Need = Max - Allocation |
|------|-------------|--------------------|--------------------------|
| P0 | (7,5,3) | (0,1,0) | (7,4,3) |
| P1 | (3,2,2) | (2,0,0) | (1,2,2) |
| P2 | (9,0,2) | (3,0,2) | (6,0,0) |
| P3 | (2,2,2) | (2,1,1) | (0,1,1) |
| P4 | (4,3,3) | (0,0,2) | (4,3,1) |

安全性检测：

1. `Work = (3,3,2)`。能满足 Need 的有 P1 (1,2,2) 与 P3 (0,1,1)。选 P1，完成后释放 Allocation：`Work = (5,3,2)`。
2. `Work = (5,3,2)`。能满足的有 P3 (0,1,1) 与 P4 (4,3,1)。选 P3：`Work = (7,4,3)`。
3. `Work = (7,4,3)`。能满足的有 P0 (7,4,3)、P2 (6,0,0)、P4 (4,3,1)。选 P0：`Work = (7,5,3)`。
4. 选 P2：`Work = (10,5,5)`。
5. 最后选 P4：`Work = (10,5,7)`。

所有进程都能进入序列，因此状态**安全**，一个安全序列为 $\langle P_1, P_3, P_0, P_2, P_4\rangle$。安全序列不唯一。

若此时 P1 请求 `(1,0,2)`：试探后 `Available = (2,3,0)`、P1 的 Allocation $= (3,0,2)$、Need $= (0,2,0)$。重新做安全性检测仍能找到安全序列（P1→P3→P0→P2→P4 或类似），因此该请求被批准。若 P0 请求 `(0,2,0)`：试探后 `Available = (3,1,2)`，此时 P1、P3、P4 的 Need 都无法被 Work 满足，状态不安全，请求被拒绝、P0 等待。

### 适用前提与局限

算法在理论上优雅，但实际商用操作系统几乎不使用，原因在于：

1. **最大需求必须预先声明**：大多数进程在运行前无法准确知道自己需要多少资源；声明过大降低利用率，声明过小则可能请求越界被拒。
2. **进程数与资源数固定**：模型假设进程数量、资源数量在运行期间不变，无法处理进程动态创建/退出。
3. **进程不能中途退出或崩溃**：若一个已分配资源的进程异常退出而不释放资源，簿记被打破。
4. **每次分配都做 $O(mn^2)$ 检测**：在大规模系统中开销显著。
5. **保证"最坏情况"安全**：即使实际不会发生最坏并发申请，也必须保留足够资源让安全序列存在，导致资源利用率长期偏低。

因此真实系统更常用"鸵鸟策略"（Linux/Windows）或在应用层规定**统一的锁获取顺序**来破坏循环等待条件。

### 常见误区

- **安全序列唯一**：错。只要存在至少一个即可；算例中 $\langle P_1, P_3, P_4, P_0, P_2\rangle$ 也可能是安全序列，安全性算法找到第一个即可。
- **不安全状态 = 死锁**：错。不安全状态只是说"没有数学保证"，实际上进程可能不会同时达到最大需求，系统仍可能不死锁。
- **银行家算法用于死锁检测**：错。它属于**死锁避免**，在分配前阻止不安全状态；死锁检测是事后用等待图或类似算法判断是否已经发生死锁。
- **Need 是独立维护的输入**：实际上 `Need = Max - Allocation` 是导出量。
- **"银行家"指银行系统使用它**：恰恰相反，真实银行系统并不用这个算法做信贷风控，它只是一个教学隐喻。
