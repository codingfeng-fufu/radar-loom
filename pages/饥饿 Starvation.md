# 饥饿 Starvation

## 核心内容

饥饿（Starvation）是并发系统中的一种**活性失败（liveness failure）**：一个进程或线程虽然**可以执行、也没有被永久阻塞**，但由于调度或资源分配策略持续偏向其他进程，导致它长期（理论上可无限期）得不到所需资源，无法推进。

饥饿与死锁的本质区别：死锁进程在逻辑上已不可能自行推进，形成循环等待；饥饿进程**理论上仍可推进**——只要竞争者释放资源、调度器轮到它，它就能继续。问题在于策略没有保证"最终会轮到它"。饥饿与活锁的区别：活锁进程在主动运行、持续改变状态做无用功；饥饿进程可能根本没有被调度到，处于可运行但长期不被选中的状态。

在活性属性的形式化分层中，**无饥饿（no starvation / starvation-freedom）** 强于无死锁和无活锁：它要求每个进程都能**最终（eventually）** 获得资源并完成，也称为"无界等待（bounded waiting）"或"无锁但有公平保证"。

### 常见成因

#### 1. 优先级调度

在基于优先级的抢占式调度中，如果系统中持续存在高优先级进程，低优先级进程可能永远得不到 CPU。这不是 bug，而是优先级调度的固有风险——高优先级任务的响应性以牺牲低优先级任务为代价。

#### 2. 优先级反转（Priority Inversion）

优先级反转是饥饿的一种经典且危险的特殊情形：一个高优先级任务等待低优先级任务持有的锁，而一个中优先级任务抢占了低优先级任务，导致高优先级任务被中优先级任务间接阻塞。等待链为：

$$\text{高优先级任务} \xrightarrow{\text{等待锁}} \text{低优先级任务（持锁）} \xrightarrow{\text{被抢占}} \text{中优先级任务（运行中）}$$

高优先级任务实际上在等待一个不相关的中优先级任务完成，这违反了优先级调度的初衷。

**经典案例：火星探路者号（Mars Pathfinder, 1997）**

1997 年登陆火星的探路者号着陆器在表面上会偶发性地触发系统复位（reset）。调查发现根因是 VxWorks 实时操作系统中的优先级反转：

- 一个高优先级的总线管理任务（负责通信）等待一个互斥锁。
- 该锁被一个低优先级的气象数据任务持有。
- 当低优先级任务持有锁时，多个中优先级的长运行任务抢占了它，导致低优先级任务无法释放锁。
- 高优先级任务因此长时间无法执行，触发了看门狗定时器（watchdog timer），系统复位以恢复。

修复方法是在创建互斥锁时启用**优先级继承协议（priority inheritance）**：低优先级任务持有被高优先级任务等待的锁时，临时继承高优先级，使其能以高优先级运行并尽快释放锁，从而防止中优先级任务抢占。这是优先级反转最著名的真实案例，事后分析由 Mike Delany 撰写，成为软件工程经典。

#### 3. 不公平的锁实现

许多锁实现（包括早期的 Java `synchronized`、某些自旋锁）在锁释放时不保证等待队列的 FIFO 顺序，可能导致某个线程反复在竞争中失败。如果新来的线程总能在等待线程之前抢到锁，等待者就饥饿了。

#### 4. 读者—写者问题

读者—写者锁有两种偏好：

- **读者优先**：只要有读者在读，后续读者可以直接进入；写者必须等所有读者离开。如果读者持续到来，写者可能永远无法获取写锁——写者饥饿。
- **写者优先**：一旦写者到达，后续读者被阻塞等待写者完成。如果写者持续到来，读者可能饥饿。

需要在实现中引入公平策略（如排队、按到达顺序服务）来避免任一方饥饿。

#### 5. 护航效应（Convoy Effect）

在 FCFS（先来先服务）或粗粒度锁的系统中，一个长时间运行的进程持有锁时，所有需要该锁的短进程排成等待队列。即使短进程只需要锁极短时间，也必须等长进程完成。这降低了整体吞吐量，且短进程相对于长进程处于结构性劣势——虽然 FCFS 本身不导致严格饥饿（等待有界），但在混合负载下会产生类似饥饿的不公平性。Blasgen 和 Gray 在 1970 年代末对 System R 的分析中命名并讨论了这一现象。

#### 6. 资源泄漏与不公平分配

如果进程获取资源后不释放（崩溃或 bug），等待该资源的其他进程将永久饥饿。类似地，某些资源分配器在多实例资源场景下可能持续把资源分配给"更积极"的请求者，忽略等待更久的请求者。

### 与死锁、活锁的对比

| 维度 | 死锁 Deadlock | 活锁 Livelock | 饥饿 Starvation |
|------|--------------|--------------|----------------|
| 进程是否阻塞 | 是，永久等待 | 否，持续运行 | 否，可执行但长期不被调度 |
| 状态是否改变 | 不变 | 不断改变 | 可能改变（被偶尔调度） |
| CPU 消耗 | 无 | 有，被浪费 | 受害者几乎无 CPU |
| 是否可能自行恢复 | 否 | 可能（若有随机性） | 可能（竞争者离开后） |
| 根本原因 | 循环等待资源 | 对称响应导致无效循环 | 调度/分配策略不公平 |
| 典型解法 | 预防/避免/检测恢复 | 随机退避、仲裁 | 老化、公平锁、优先级继承 |
| 活性强度 | 最弱 | 中 | 最强（保证每个进程最终完成） |

### 缓解与预防

#### 1. 老化（Aging）

老化是最经典的防饥饿技术：进程在就绪队列中等待越久，其有效优先级越高。设进程静态优先级为 $P_0$，已等待时间为 $w$，老化后的有效优先级为：

$$P_{\text{eff}} = P_0 + f(w)$$

其中 $f(w)$ 是关于等待时间的非递减函数，例如 $f(w) = \lfloor w / T \rfloor$（每等待 $T$ 个时间单位优先级加 1）。这保证任何进程等待足够长时间后优先级都会超过所有竞争者，最终被调度。老化在许多通用调度器中以不同形式存在。

#### 2. 公平锁与 FIFO 排队

使用 FIFO 等待队列的锁（如 Java 的 `ReentrantLock(fair=true)`、Linux 的 `futex` 排队、 ticket lock）保证锁按请求顺序授予，每个等待者在有界时间内获得锁。代价是吞吐量可能低于非公平锁（不能让恰好正在运行的线程"顺路"抢锁），但消除了饥饿。

#### 3. 优先级继承协议（Priority Inheritance Protocol, PIP）

如 Mars Pathfinder 的修复：当高优先级任务等待低优先级任务持有的锁时，低优先级任务临时继承高优先级，直到释放锁。这消除了中优先级任务的抢占窗口。注意 PIP 不能防止死锁，且可能产生链式优先级继承（A 等 B 的锁、B 等 C 的锁，则 C 继承 A 的优先级）。

#### 4. 优先级天花板协议（Priority Ceiling Protocol, PCP）

比 PIP 更强的协议：每个锁有一个"优先级天花板"（等于所有可能获取该锁的任务的最高优先级）。任务获取锁时，其优先级立即提升到天花板，防止其他高优先级任务在它持锁期间抢占。PCP 可以防止死锁和链式阻塞，但实现更复杂，可能造成不必要的优先级提升。

#### 5. 公平的读者—写者实现

- **带队列的实现**：所有读者和写者进入同一个 FIFO 队列，按到达顺序服务。写者到达后，其后续读者必须等待，避免写者饥饿。
- **偏向写者但有读者老化**：写者优先，但读者等待超过阈值后获得优先权。
- Linux 的 `rw_semaphore` 使用等待队列，在实现上偏向写者以避免写者饥饿。

#### 6. 有界等待（Bounded Waiting）

在同步原语的设计中，显式保证"进程在获取锁之前最多等待 $N$ 个其他进程通过"（如 Peterson 算法、Bakery 算法、ticket lock）。这是从算法层面消除饥饿的理论保证。

### 检测的难点

- 饥饿不像死锁那样有明确的"循环等待"结构可检测，它往往是渐进的、统计性的。
- 需要监控**等待时间分布**而非平均值——平均等待时间正常不代表没有长尾饥饿。
- 饥饿可能只在特定负载组合下出现（如持续到来的高优先级任务），难以在测试中复现。
- 生产环境中通常通过**超时机制**间接发现：等待资源超过阈值后主动放弃、告警或重新排队，而不是精确检测"是否正在饥饿"。

### 常见误区

- **饥饿就是低优先级任务执行慢**：不是。慢但仍在推进不是饥饿；饥饿是长期得不到资源、几乎不推进。优先级低本身不构成饥饿，只有当低优先级任务被无限期推迟时才是。
- **死锁一定伴随饥饿**：死锁进程确实都无法推进，但"饥饿"特指在不公平策略下某进程被持续跳过；死锁是结构上的循环等待，原因不同。
- **FCFS 不会导致饥饿**：FCFS 理论上保证有界等待（每个请求最终按序服务），但护航效应在实际中造成极差的响应时间；在资源动态分配且请求可取消的场景下，FCFS 仍可能因请求反复重排而产生饥饿。
- **优先级继承能解决所有优先级问题**：PIP 解决优先级反转，但不解决死锁（可能链式阻塞），且有运行时开销；某些场景需要 PCP 或其他协议。
- **老化等于动态优先级调度**：老化是基于等待时间的被动提升，与根据任务行为主动调整优先级的调度不同。
- **饥饿只发生在 CPU 调度中**：锁竞争、I/O 调度、网络包调度、数据库事务锁、分布式共识等任何存在资源竞争和优先级/顺序的地方都可能发生饥饿。

## 和我的项目的关系

暂无直接关联。饥饿所揭示的"公平性与吞吐量之间的权衡"是任何资源受限系统的核心设计问题；在设计检索系统、任务队列或多智能体协调机制时，应检查是否存在某类请求被持续跳过的风险，必要时引入老化或公平排队。
