# 技术雷达知识库：实习展示稿

> 这是项目展示和面试讲解稿，不是日常维护手册。数字以当前本地仓库为准，随日常使用增长。

## 一句话介绍

技术雷达是一个我为长期学习和研究建立的本地优先、Git 可追溯的 Markdown 知识工程系统：它把知识采集、结构化写作、全文搜索、知识图谱、动态分类、健康检查和 Claude Code 协作组合在一条可回放的日常工作流中。

## 为什么做它

一次性的对话和笔记很容易丢失。我需要一个系统来持续回收：

- 将阅读和实验中有价值的内容沉淀为可搜索页面；
- 防止同一概念被重复建页；
- 记录来源、交叉引用和修改历史；
- 让 Claude 在项目根目录内可控地读取、更新和检查知识。

## 当前规模

2026-08-11 的本地生成和 Git 统计：

- 134 个概念页、5 个项目页和 8 个工程面试页；
- 主知识图谱有 148 个节点、855 条边，断链为 0；
- 20 个 Python 脚本、26 个 Python 测试文件，脚本与测试合计约 7,913 行；
- 从 2026-07-04 开始有 207 次 Git 提交，分布在 21 个活跃提交日；
- 按提交前缀统计，包含 41 次功能、30 次修复、40 次文档、60 次知识摄入和 18 次测试相关提交；
- 最近的知识摄入包括 Adam 优化器、表格基础模型、A2A 协议、操作系统和 RAG 等主题。
- `ideas/` 是独立 Idea Lab，用于保存原始想法、失败尝试和重启条件，不混入主知识图谱。

## 系统架构

```text
原始对话 / PDF / URL / 文本
              |
              v
       raw/inbox/ 和 papers/
              |
              v
      Claude Code 结构化建页
              |
              v
 pages/*.md + frontmatter + [[双链]]
              |
     +--------+---------+----------------+
     |                  |                |
     v                  v                v
 _index.md       taxonomy.json      graph-data.json
 检索索引       动态分类          Cytoscape 图谱
     |
     v
 check_health.py + Git 提交 + Web Viewer
```

Web 操作台由两个本地服务组成：

- `18080`：一体化操作台和 Claude Code WebUI；
- `18081`：Markdown Viewer、图谱、索引和刷新 API。

两个 iframe 通过版本化 `postMessage` 协议传递当前文件、图谱状态和刷新完成回执，右侧 Claude 会话不会因知识库刷新而丢失。

## 核心能力

### 1. 增量知识采集

- 一个概念一个页面，新进展回到原页更新。
- 建页前执行标题、别名和语义三层查重。
- frontmatter 统一保存来源、摘要、信度和分类。
- 保留可审计的原始材料和 Git 修改记录。

### 2. 索引、动态分类与图谱

- `build_index.py`：从 Markdown frontmatter 生成检索索引。
- `taxonomy_cli.py`：增量同步、全局重组、状态和校验。
- `render_graph.py`：生成关系图谱、分类子图和 JSON 数据。
- Cytoscape.js + fCoSE：支持搜索、聚焦、类别筛选和 Viewer 跳转。
- 分类快照保留上一版有效结果，失败时不发布部分结果。

### 3. 质量与可回放

`check_health.py` 检查：

- frontmatter 格式
- 双链断链
- 来源存在性
- 摘要完整性
- 索引同步
- LaTeX 公式定界符
- 图谱与页面一致性

### 4. Claude Code 集成

- 在项目根目录中运行 Claude Code。
- 通过 `$create-knowledge-page` 创建高质量知识页。
- 通过 `$capture-idea` 整理独立 Idea。
- 通过读论文 Skill 从 PDF 到结构化笔记。
- WebUI 支持 normal、plan、accept edits 和 dangerously skip permissions 四档权限模式。

## 工程难点

### 日常可用性与数据生命周期

系统不只是 Markdown 文件夹，还要处理：

- 新页面如何进入索引和图谱；
- 分类重组失败时如何保留旧快照；
- 刷新时如何保留当前页面、图谱位置和 Claude 草稿；
- 外层操作台与内层 iframe 如何确认操作完成。

### 安全边界

- 服务只监听本机。
- WebUI 工作目录固定为知识库根目录。
- 刷新 API 只调用固定脚本，不接受前端传入任意命令。
- 跨 iframe 消息检查 origin、source 和版本。
- 支持危险模式，但由使用者显式切换。

## 真实维护案例

### 案例 1：服务端成功，前端却报刷新超时

现象是后端 `POST /api/refresh` 已经返回 200，但 Idea Viewer 和 Idea 图谱仍在 30 秒后显示“未确认完成”。定位后发现外层操作台需要 iframe 返回 `kb-refresh-result`，而新增的两个 Idea 页面没有实现该协议。

处理包括：

- 为两个页面增加受信 origin/source 检查和完成回执；
- 刷新 Idea 列表时保留当前选中项；
- 刷新图谱时销毁旧 Cytoscape 实例，避免重复画布和事件累积；
- 通过真实浏览器验证列表、图谱和草稿保留。

### 案例 2：Markdown 、数学公式和 Claude 回答渲染

日常阅读中出现过 `**` 未渲染、复杂 `cases` 公式不稳定和 Claude 对话排版难读等问题。项目最终将 Markdown、KaTeX、Mermaid、Highlight.js 和 DOMPurify 固定为本地资源，并将数学定界符要求加入知识页协议和健康检查。

这个案例的关键不是“换一个 Markdown 库”，而是将写作规则、渲染链路和自动校验连成闭环。

### 案例 3：两个本地服务的端口职责被破坏

一次 Claude 误将 `18080` 上的 WebUI 进程终止，并把知识库服务启动到同一端口。结果是页面看似可打开，但 Claude 的 `/api/chat` 返回 404。

恢复时没有粗暴停掉所有 Python/Node 进程，而是：

- 核对 `18080/18081` 的真实 PID 和日志；
- 只终止错误的 `serve_kb.py` 进程；
- 通过项目控制脚本恢复 WebUI；
- 分别验证操作台、Markdown 原文和 Claude 输入框。

这个案例体现了服务边界、日志诊断和最小恢复范围的工程思维。

## 演示顺序

1. 打开 Web 操作台。
2. 搜索一个概念并打开页面。
3. 点击交互图谱，展示节点、边和分类结构。
4. 在当前页面点击“询问 Claude”，展示当前路径如何进入提示词。
5. 用“创建知识页”演示查重、来源、模板和健康检查。
6. 点击顶部刷新，展示索引、分类、图谱更新，同时保留 Claude 会话和草稿。

## 客观限制

- 目前是单用户本地工具，不是多用户 SaaS。
- 分类和命名仍受本地模型、运行环境和可用 API 配额影响。
- 图谱大规模渲染、跨文档同义对齐和多人协作还不是当前目标。
- 知识页的最终正确性仍需要人工审阅，自动检查主要保证结构与可追溯性。
