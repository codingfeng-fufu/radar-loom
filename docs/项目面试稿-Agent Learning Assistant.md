# Agent Learning Assistant（智学伴侣）

## 一句话介绍

这是一个面向 AI Agent 学习场景的本地优先学习助手：它把知识库问答、工具调用、学习规划、概念图谱、进度追踪和长期记忆组合成一个可运行、可评估的 Agent 工作台。

## 30 秒回答

我做了一个帮助用户学习 AI Agent 技术的本地 Web 助手。它不是简单的聊天机器人，而是由 Agent 负责交互和任务路由，RAG 负责提供知识依据，工具层负责执行代码、更新进度和生成学习计划，记忆层负责保存长期有价值的信息。检索侧使用 FAISS 和 BM25 混合召回，并在最终回答后用 Self-RAG 检查是否有知识库依据。当前 2051 个文档块的检索 smoke 测试 30/30 通过，需要检索的问题上 faithfulness 和 context recall 均为 1.0。

## 1. 项目背景

### 为什么做

学习 Agent、RAG 和工具调用时，单次问答容易丢失上下文，也无法持续记录学习进度。项目希望把“问问题、查资料、执行工具、制定计划、复习和沉淀记忆”放进同一条工作流。

### 要解决的问题

- 只用向量检索时，关键词和专有名词可能召回不稳定。
- Agent 的工具参数格式不稳定，直接执行容易失败。
- 使用了 RAG 不代表最终回答一定被资料支持。
- 所有对话都写入长期记忆会污染后续上下文。

## 2. 系统整体架构

## 2A. 谁使用、谁买单

直接用户是学习 Agent、RAG 和大模型工程的个人开发者、学生或企业培训学员；买单方可能是个人订阅者、企业培训部门和教育机构。购买理由是减少资料整理、学习计划维护和重复答疑的成本，并把学习过程沉淀为可追踪状态。当前版本更适合作为个人或培训场景的工作台，尚未定位成大规模教育平台。

```text
用户问题
   |
   v
HarnessExecutor / Agent
   |---- 学习工具、进度工具、代码工具、计划工具
   |
   +--> HybridRetriever
   |       |-- FAISS 向量召回
   |       |-- BM25 稀疏召回
   |       |-- RRF 融合 + 邻居 chunk 扩展
   |       '-- 上下文构造
   |
   +--> MemoryManager：用户画像 + 情景记忆
   |
   '--> Self-RAG：回答依据检查与修复
                |
                v
          React/Vite Web 工作台
```

主要目录：`rag/`、`agent/`、`harness/`、`tools/`、`memory/`、`planning/`、`frontend/`、`evaluation/`。

## 3. 我的个人贡献

- 负责 Agent、RAG、工具调度、记忆、规划和 Web 工作台的整体集成。
- 设计 FAISS + BM25 混合检索、RRF 融合和邻居 chunk 扩展流程。
- 实现工具参数归一化、校验和失败兜底，兼容 JSON、Python dict 字符串和自然语言输入。
- 实现回答后的 Self-RAG 依据检查，以及不受支持时的修复流程。
- 搭建评估、集成检查、启动 smoke 和浏览器 smoke，形成可复现的交付链路。

## 4. 核心技术实现

### 4.1 混合检索、融合与上下文补全

**问题：**纯向量检索对“Self-RAG”“FAISS”“ReAct”等专有词和代码标识不一定稳定，纯 BM25 又无法很好处理自然语言改写。

**方案：**先判断问题是否需要知识库，再生成适合不同检索器的查询。FAISS 负责语义召回，BM25 负责关键词召回；多路结果通过 Reciprocal Rank Fusion 统一排序，同时保留每路的高排名 seed，避免某一路排序异常把关键文档完全挤掉。命中 chunk 后，按 `(source, chunk_id)` 补充前后邻居，恢复定义、条件和结论之间的上下文。

**取舍：**邻居扩展会增加上下文长度和 token 成本，因此只对最终候选做扩展并限制总量；RRF 不需要训练，但需要通过 smoke 和 QA benchmark 检查融合后是否真的改善召回。

### 4.2 Agent 路由与工具调用可靠性

**问题：**学习助手既要回答知识问题，也要更新进度、生成计划、执行代码和浏览概念图。LLM 可能输出 JSON、Python dict 字符串、`key=value` 或自然语言，直接把原始参数交给工具会导致大量失败。

**方案：**请求先进入 `HarnessExecutor`，由 Agent 决定是否调用工具；工具调用经过 `normalize_tool_input` 归一化，再经过字段 validator、枚举检查和数量限制，最后才进入具体执行器。解析失败、校验失败和执行异常分别提供明确的 fallback，保证一次工具失败不会拖垮整轮对话。

**取舍：**增加了确定性代码和维护成本，但把错误从“不可预测的模型输出”收敛成“可测试的工具协议”，更适合面试演示和长期维护。

### 4.3 Self-RAG 证据校验与修复

**问题：**调用过 RAG 不代表最终答案完全依据检索内容，模型仍可能补充上下文没有支持的解释。

**方案：**回答生成后读取本轮 retrieval state，由 Self-RAG controller 判断答案是否被上下文支持。`SUPPORTED` 直接返回；不支持时进入 repair 流程，要求模型只根据参考上下文重写；没有检索或没有有效上下文时跳过校验，避免把普通闲聊误判为幻觉。

**取舍：**增加一次模型调用和延迟，但换来了可解释的证据边界。项目把“检索命中”和“最终回答有依据”拆成两个可独立评估的环节。

### 4.4 长期记忆与学习状态

**问题：**把所有历史对话注入上下文会造成噪声、成本和隐私风险；完全不记忆又无法形成持续学习体验。

**方案：**`MemoryManager` 将信息分成用户画像和情景记忆。每轮通过重要性评分器做门控，只有超过阈值的内容才抽取进入情景记忆；画像持续更新，检索时根据当前问题选择相关记忆。学习进度、计划和概念关系则作为结构化状态单独保存。

**取舍：**门控可能漏掉低频但重要的信息，所以保留人工更新进度和显式工具入口，不让自动记忆成为唯一写入路径。

## 5. 最难的问题

### 难题一：模块很多，但必须保持状态一致

Chat、Plan、进度、概念图和代码工作区都可能改变用户状态。解决方式是把请求入口、工具执行结果、记忆写入和 Web 状态更新放进统一的 harness 流程；工具返回结构化结果，前端再根据结果更新对应工作区，而不是让每个页面各自猜测状态。

### 难题二：如何定位“回答错了”到底是哪一层的问题

回答错误可能来自查询理解、召回、上下文拼接、生成或工具执行。项目保留 retrieval state、路由 trace 和评估结果，把链路拆成“是否需要检索—召回了什么—上下文是否足够—答案是否被支持”四个检查点，避免只看最终字符串做黑盒调试。

### 难题三：失败时如何降级，而不是整条链路崩溃

项目对模型调用、JSON 解析、工具执行、检索和 Web 服务分别设置边界：工具有 validator/fallback，RAG 异常返回无检索结果，Self-RAG 异常采用保守放行，启动前通过 health check 和 smoke 检查依赖。这样单个可选能力失败时仍能保留基础聊天能力。

### 难题四：指标要能复现，而不是只展示一次漂亮结果

评估脚本固定输入文件、指标阈值和输出报告，区分 retrieval smoke、RAGAS、集成检查和浏览器 smoke。指标异常时可以回到具体样例和 repair 记录，而不是只重新运行一次 demo。

## 6. 项目结果与量化验证

### 6.1 检索规模与基础正确性

| 指标 | 结果 | 说明 |
|---|---:|---|
| 知识库文档块 | 2051 | 当前本地 FAISS 索引规模 |
| Retrieval smoke | 30/30 | 固定 smoke 样例全部通过 |
| Smoke 通过率 | 100% | 未发现召回失败样例 |

### 6.2 需要检索的问题：RAGAS

| 指标 | 结果 | 面试解释 |
|---|---:|---|
| Faithfulness | 1.0000 | 生成答案与检索上下文一致 |
| Answer relevancy | 0.8604 | 答案与问题的相关性较高，仍有表达优化空间 |
| Context precision | 0.9940 | 检索上下文中绝大多数内容与问题相关 |
| Context recall | 1.0000 | 评估样例需要的信息均被召回 |

报告同时记录了 2 次 faithfulness repair 和 3 次 answer relevancy repair，说明系统不是只统计成功样例，也保留了修复路径。

### 6.3 全链路工程验证

- 集成检查覆盖后端、前端构建、启动 smoke 和接口联调。
- 浏览器 smoke 覆盖 Chat、Plan、图谱、代码、进度和工具页面。
- README 提供 CPU 基线、GPU 可选路径和统一 `make check` / `make web-check` 入口。

### 6.4 指标边界

这些结果来自本地固定评估集，不等同于线上用户成功率；当前项目也没有声称多用户并发、长期在线稳定性或外部实时知识的效果。面试时应把“评估集上的证据一致性”与“生产环境整体质量”明确区分。

## 7. 现场演示顺序

1. 从 Chat 提问一个需要知识库的 Agent 概念问题。
2. 展示检索依据和最终回答校验。
3. 切换到概念图谱，展示相关节点和学习路径。
4. 让 Agent 生成学习计划并更新进度。
5. 演示代码工具或工具参数异常时的兜底结果。

## 8. 可能追问

### 为什么不用单一向量检索？

专有名词、缩写和代码术语需要关键词精确命中；BM25 与向量召回互补，再用 RRF 降低单一路径失误的影响。

### Self-RAG 和普通 RAG 有什么区别？

普通 RAG 只负责提供上下文，Self-RAG 还检查最终答案是否被上下文支持，并在不支持时触发修复。

### 为什么不把所有对话都存进记忆？

记忆会增加上下文成本并引入噪声，所以使用重要性门控，只持久化对后续学习有价值的内容。

### 这个项目的限制是什么？

它目前是单用户本地优先系统，模型和外部服务仍会影响运行；自动校验主要保证证据与结构，不能替代人工判断。

## 9. 1 分钟总结

这个项目的核心不是“接了一个聊天模型”，而是围绕 Agent 的可靠使用补齐了检索、工具、记忆、规划和评估环节。我的重点工作是把这些模块组织成可运行的闭环，并针对检索漏召回、工具参数错误和无依据回答设计了对应的工程防护。最终系统既能现场演示，也有检索 smoke、RAGAS 和集成测试支撑。
