# 同心杯金融知识平台

## 一句话介绍

这是一个面向统计年报、行业台账和经营报表的文档分析系统：常规问题走原文证据问答，数值问题走结构化事实检索和程序计算，预测问题走隔离的历史序列建模。

## 30 秒回答

传统 PDF 问答擅长找相似段落，但不擅长从表格中稳定抽取年份、指标、单位并完成求和、同比或预测。我参与设计并实现了一个七模块系统：先把 PDF 解析成可追溯的文本和表格 Chunk，再抽取实体与结构化事实，分别建立辅助 RAG 库和核心事实库。在线查询时由路由器严格二选一：常规问题用原文和可选 Neo4j 证据回答，数值问题由程序用 Decimal 按固定模板计算，预测问题用真实时间坐标拟合线性回归。这样把大模型负责的理解和程序负责的计算分开，降低数值幻觉。

## 1. 项目背景

### 需要解决的问题

- PDF 中正文、表格、扫描件和复杂版式难以统一解析。
- 数值在切块或抽取时容易丢失年份、单位、维度和主体。
- 语义检索能够找到相关内容，但不能保证直接完成统计计算。
- 让大模型自由生成公式和算术过程，容易出现事实选择、算子顺序和计算错误。
- 结果需要回到原始文档页码和片段，不能只给一个无法解释的数字。

### 核心设计原则

原文证据负责解释和引用，结构化事实负责筛选和计算；大模型负责识别、选择和语义适配，程序负责校验、计算、时间处理和引用合法性。

## 2. 系统整体架构

## 2A. 谁使用、谁买单

直接用户是行业研究员、政策分析人员、银行和券商的数据团队；买单方可以是金融机构、咨询公司或政府研究部门。它替代的是人工翻阅 PDF、录入表格、重复计算和结果回溯的成本，价值在于把报表变成可检索、可计算、可追溯的数据服务。MVP 还不是生产 SaaS，正式采购前需要补齐数据接入、权限、并发和运维能力。

```text
离线构建
PDF -> 模块一：解析、清洗、表格识别、Chunk
    -> 辅助 RAG 库（原文 Chunk）
    -> 模块二：实体/事实抽取、去重、还原句
       -> 核心事实库（事实还原句）
       -> Neo4j（Entity / Fact）

在线问答
用户问题 -> 模块五：查询规划与二选一路由
    -> general_qa -> 辅助 RAG + 可选固定图查询 -> 证据约束回答
    -> quantitative_analysis -> 核心事实库 -> 统计模板 / 线性回归
```

七个模块分别负责 PDF 预处理、知识抽取、双向量库、图谱存储、查询路由、数值分析和常规回答。两条在线路线互斥，不跨库合并，也不互相回退。

## 3. 我的个人贡献

- 参与七模块系统的总体架构和模块边界设计。
- 设计“原文 Chunk / 结构化事实”双数据链路，以及 `document_id`、`chunk_id`、`fact_id`、`dataset_version` 四级追溯标识。
- 参与双物理向量库、FAISS + BM25 + Reranker 检索链路和 Neo4j 固定查询接口设计。
- 设计查询规划的 `general_qa` / `quantitative_analysis` 二选一路由。
- 设计统计模板、事实绑定、Decimal 确定性计算和预测数据隔离规则。
- 参与模块级测试、验收数据集和版本一致性检查方案。

## 4. 核心技术实现

### 4.1 PDF 到可追溯 Chunk

模块一按页处理 PDF：原生文本优先使用 PyMuPDF，不可用时按条件调用 OCR；表格由视觉模型识别，并从正文区域剥离成独立表格 Chunk。文本采用“标点初切 + 语义合并 + 业务结构保护”，每个 Chunk 保留文档、页码、区域和处理状态。

只有 `processing_status=ready` 的 Chunk 能进入下游；解析失败或输入超限的数据会显式标记，不能静默进入索引。这保证了后续抽取不会把坏数据当成正常证据。

### 4.2 知识抽取与事实重构

对 ready Chunk 执行实体识别、候选实体召回与对齐、开放关系抽取、一次 Data Gleaning、精确去重和事实还原句生成。每条事实至少包含主体、关系、对象、原文时间、数值、单位、维度、来源 Chunk 和稳定 `fact_id`。

MVP 不强行建立完整本体，也不让模型自由修正时间和数值；时间保留原文表达，事实通过稳定 ID 和来源集合进行合并，避免重复事实覆盖证据。

### 4.3 双物理向量库

系统维护两个完全隔离的库：`auxiliary_rag` 存原文和表格 Chunk，服务常规问答；`core_fact` 存事实还原句和完整事实字段，服务统计与预测。每个库拥有独立的 FAISS、BM25、SQLite 元数据和构建快照。

单个库内部固定执行 FAISS Top 50、BM25 Top 50、record ID 并集去重和 Cross-Encoder Rerank。常规问答返回精排 Top 5，核心事实库保留候选池全部精排结果，由计算模块继续做事实筛选。

### 4.4 严格二选一路由

模块五只调用一次通用大模型，输出 `route_type`、检索问题、实体、关系和时间。`general_qa` 处理概念、背景和流程问题；`quantitative_analysis` 处理统计、比较、增长率和预测问题。

路由失败时直接返回 `routing_failed`，不调用下游模块；常规路线不会访问核心事实库，数值路线不会访问辅助 RAG 或 Neo4j。这样避免一个模糊问题同时触发多套证据，导致结果不可解释。

### 4.5 确定性统计与预测

统计任务使用预注册模板：`lookup`、`sum`、`average`、`count`、`max`、`min`、`difference`、`ratio`、`growth_rate`。大模型只能选择模板、候选事实和 `fact_id`，不能生成公式或最终数字；程序校验主体、关系、单位、维度和时间范围后，用 Decimal 完成计算。

预测任务只使用目标时间之前、同一主体/指标/单位/维度的历史事实，按真实时间坐标临时拟合单变量线性回归。至少需要两个不同时间点，不自动补齐缺失年份；同一时间存在冲突数值时直接返回无法预测。

## 5. 最难的问题

### 难题一：如何避免大模型直接“算错”

把模型职责限制为“选模板、选事实、绑定角色”，把公式、算术和单位检查交给程序。模型即使选错事实，也会在程序校验阶段暴露，而不是生成一个看似合理的数字。

### 难题二：两种证据如何避免混用

原文证据适合解释，结构化事实适合计算。项目用两个物理隔离的向量库和严格路由保证边界，并要求同一 `dataset_version` 同步构建向量库和图谱，避免索引与图谱版本不一致。

### 难题三：抽取结果如何回到原文

`fact_id -> source_chunk_ids -> chunk_id -> document_id / page` 形成追溯链。常规回答引用 Chunk，统计和预测返回使用过的 fact_id，用户可以继续定位到原始 PDF。

### 难题四：预测结果如何防止数据泄漏

程序按原文时间生成真实时间坐标，排除目标时间及之后的事实，不补齐缺失点，不跨问题保存模型参数。同一时间冲突时关闭预测，而不是擅自选择一个值。

## 6. 项目结果与量化验证

### 已落地的工程能力

- 七个模块均有独立职责、输入输出契约和验收文档。
- 模块一至模块四已有对应 Python 包、测试和交付物结构。
- 双向量库使用独立 FAISS、BM25、SQLite 元数据和 manifest，并支持构建校验后原子激活。
- Neo4j 导入前检查模块二与模块三的 `dataset_version`，版本不一致时拒绝写入或查询。
- 统计计算固定使用 Decimal，预测使用临时线性回归，不保存跨问题参数。

### 验收规模与门槛

模块一正式质量验收设计要求至少 12 份 PDF、120 页、60 条正文标注、40 张表格标注和 100 个年份/数值/单位标注；模块二要求实体、三元组、数值事实和重复事实冻结标注，并准备 FR2KG 离线基准子集；模块三使用公开 C-MTEB/T2Retrieval 数据验证 Recall@5。

这些是验收设计中的冻结门槛，不应在没有完成对应数据集和正式运行的情况下直接表述为最终通过成绩。

### 可展示的结果口径

面试中可以准确说：项目已完成七模块 MVP 设计和核心模块实现，建立了从 PDF、Chunk、Fact、向量库/图谱到问答或计算结果的端到端闭环，并为每个关键模块准备了可重复的测试和验收入口。对于具体 Recall、抽取 F1 或预测误差，应以正式验收报告中的实际运行结果为准。

## 7. 现场演示顺序

1. 上传一份含表格的统计年报，展示正文和表格 Chunk 的来源信息。
2. 提问“某指标在若干年份的合计/同比”，展示路由到 quantitative_analysis。
3. 展示候选事实、模板、fact_id 绑定和 Decimal 计算结果。
4. 点击引用回到原文页码，说明追溯链路。
5. 再提问一个背景或原因问题，展示 general_qa 使用原文证据回答。
6. 演示历史序列预测，并说明未来数据隔离和冲突关闭规则。

## 8. 可能追问

### 为什么不让大模型直接读表格并计算？

模型适合理解问题和选择事实，但精确计算、单位校验和时间边界应由程序完成，这样结果可复现、可测试、可追溯。

### 为什么要两个向量库？

原文 Chunk 和结构化事实的检索目标不同。物理隔离可以避免常规解释证据和计算事实混在一起，也便于分别评估和版本管理。

### 为什么不用自然语言生成 Cypher？

MVP 优先保证安全和稳定，只提供固定结构化查询接口，不允许模型生成任意 Cypher，避免查询越权和不可控的复杂图推理。

### 当前项目的限制是什么？

目前是 MVP，尚未覆盖完整本体、复杂多跳图推理、跨库融合、在线增量索引、生产级高可用和复杂预测模型。

## 9. 1 分钟总结

同心杯项目的核心不是把 PDF 接到一个大模型上，而是建立一条可解释的数据生产和问答链路：PDF 先变成带来源的 Chunk，再变成带时间、单位和 fact_id 的结构化事实；在线阶段严格区分常规问答和数值分析，前者用证据生成回答，后者由程序按模板计算。我的重点贡献是围绕数据契约、双库隔离、确定性计算和版本追溯，把大模型的不确定部分限制在可控边界内。
